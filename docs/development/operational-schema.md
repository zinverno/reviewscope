# PR-07 · Операционная схема и миграции

**NEEDS_OPERATIONAL_SCHEMA_REVIEW.** PostgreSQL хранит принадлежность данных, историю поставок и ссылки на результаты. Для воспроизведения анализа нужен конкретный DuckDB-объект с известным SHA-256. Один изменяемый файл с именем точки потерял бы старую версию при следующей поставке. API v1 и Streamlit по-прежнему читают выбранную локальную DuckDB. PostgreSQL и extra `operational` нужны только операторским инструментам ниже. [Решение о границе API](adr-api-boundary.md)

## Ключи и связи

В таблице `W` обозначает workspace, `S` — источник внутри W. Обычные внутренние ID — UUID. У backfill UUID детерминированы, чтобы повтор одного переноса имел те же ключи.

| Таблица | Ключ и кардинальность | Что фиксирует |
| --- | --- | --- |
| workspace | id | Корень владения, имя, время создания, active/archived. |
| workspace_membership | W + principal_id | По одной роли и состоянию внутреннего участника в пространстве. Principal — внутренний UUID, без логина и приглашения. |
| client_project | W + id | Именованная клиентская задача. Один workspace содержит несколько проектов. |
| location | W + project_id + id | Внутренний филиал проекта. Название может отсутствовать. |
| source | W + id; source_key уникален в проекте | Тип, безопасная метка происхождения, необязательный внешний ID и декларация политики полноты. Учётные данные сюда не передаются. |
| source_location | W + S + external_place_id | Много внешних обозначений могут указывать на один внутренний филиал. Два составных FK требуют один workspace и проект у филиала и источника. |
| import_batch | W + S + id | Неизменяемая квитанция поставки с SHA файла, версией процедуры, временем регистрации, отдельным временем получения, покрытием, счётчиками и результатом. Одинаковые байты допустимы в разных поставках. |
| review_identity | W + S + id; уникальный (W,S,external_review_id) при наличии | Точное внешнее значение относится к одному источнику. NULL означает «ID не предоставлен»; несколько таких строк допустимы. Для них нет автоматического сопоставления между поставками. |
| review_version | W + S + id; уникальный (W,S,identity_id,version_no) | Точный текст, оценка, внешний ID автора, место, дата с исходной точностью, метаданные, версия нормализации, квитанция происхождения. PostgreSQL вычисляет content_sha256 при вставке. |
| snapshot | W + id | Источник, квитанция с периодом и полнотой, JSON-фильтры, канонический список версий, SHA манифеста, SHA и серверный ключ DuckDB. |
| snapshot_member | W + snapshot_id + version_id | Реляционная проекция манифеста с FK к снимку и версии одного источника. Индекс по версии поддерживает обратный поиск. |
| analysis_run | W + id | Один снимок, версии движка, модели и определения, состояние, время создания и завершения, ID основного выходного артефакта. Несколько запусков могут читать один снимок. |
| artifact | W + id; FK на запуск в W | Один запуск имеет несколько выходов. Вид (report/json/duckdb/export), SHA-256, размер в байтах, вычисленный серверный ключ, время создания и состояние хранения. |

PostgreSQL проверяет владение составными FK в том числе при прямом INSERT. Для двух источников внешний отзыв `r1` создаёт две отдельные идентичности. Пустая строка и строка из пробелов для внешнего ID отклоняются. Метки источника, имя файла, место в конкретном экспорте и `cluster_id` расчёта не дают глобальной идентичности. Историю разрешено читать только доверенному оператору. Ограничения связей сами по себе не ограничивают SELECT и не авторизуют участников. Проверка доступа и изоляция клиентов относятся к PR-08.

## История и публикация

- Корневая версия имеет номер 1. Для N > 1 генерируемое поле `supersedes_no` и FK требуют предыдущую версию той же идентичности. Исправление текста или нормализации создаёт строку с новым ID. Хэш содержимого вычисляется из JSON-массива нормализации, автора, места, текста, оценки, времени (epoch), календарной даты и метаданных, сериализованного PostgreSQL в UTF-8. Две версии могут иметь одинаковое содержимое и разное происхождение.
- `registered_at` — время записи квитанции, `received_at` — известное время получения. Интервал покрытия — [covered_from, covered_until). Время события и регистрации хранится в TIMESTAMPTZ как момент времени. Для обмена используйте UTC и явное смещение; операторские команды ниже задают UTC. Известную только календарную дату храните в `published_date` (DATE); одновременно с `published_at` она запрещена. Для неизвестной даты оба поля NULL. Чужой локальный пояс без основания не присваивается.
- У полноты есть значения full, partial и явное unknown. NULL означает отсутствие декларации. Та же семантика пропуска действует для границ периода и каждого счётчика. Ноль означает измеренный ноль. При известных трёх счётчиках accepted + rejected = input. Отсутствие записи в частичной поставке означает только, что её не наблюдали. Старый состав и версии сохраняются. [Контракт двух поставок](pilot/data-contract.md)
- Заголовок снимка публикуется одним INSERT. Отсортированные уникальные UUID версий образуют явный манифест. AFTER INSERT создаёт все snapshot_member в той же транзакции. Собственный родительский снимок, его источник и существование каждой версии проверяются в БД. Две версии одной идентичности в одном снимке запрещены. При ошибке заголовок и все связи откатываются. Новый объект с тем же составом, другими байтами DuckDB или фильтрами получает другой digest.
- Точный вход SHA-256 манифеста — UTF-8 последовательность полей `rs-snapshot-v1`, W, S, batch UUID, DuckDB SHA, `filters::jsonb::text` и строки версий в порядке UUID. Разделитель — LF. Для пустого списка последняя строка пустая. Функция `snapshot_digest` — эталон SQL. Неизменяемая квитанция задаёт период и покрытие по ссылке. Манифест утверждает, какие версии должен представлять объект; PostgreSQL не читает внешний файл. Backfill подтверждает соответствие для конкретной синтетики.
- Run ID сохраняется в БД. Эфемерный `X-Analysis-Execution-ID` HTTP v1 служит диагностике процесса. Запуск создаётся в queued, допускает running → succeeded/failed либо queued → failed. Чтобы завершить его успешно, нужен основной артефакт **этого** запуска. Выходы регистрируются пока запуск running. Вход, версии и завершённый результат защищены от изменения. У артефакта отдельно разрешено движение available → pending_deletion → deleted. Внешнее удаление байтов пока не выполняется.
- Исторические таблицы защищают INSERT-only триггеры, ограничения ключей и запрет TRUNCATE. Изменения состояния run/artifact имеют явные переходы. Предполагается доверенный владелец БД и контролируемое хранилище объектов. Администратор с возможностью менять DDL/триггеры или файлы находится за этой границей.

## Пустая установка и перенос демо

Из корня checkout в активном virtualenv. Нужен доступ к выделенной PostgreSQL-БД и обычным клиентам PostgreSQL. Оператор выбирает сервер через libpq (`PGHOST/PGPORT/PGUSER` или `PGSERVICE`); пароль при необходимости помещается в закрытый passfile. DSN и секреты не передаются в аргументах миграции или в репозиторий.

```bash
python -m pip install -e '.[operational,dev]'
createdb -T template0 reviewscope_pr07_demo
export PGDATABASE=reviewscope_pr07_demo PGTZ=UTC
python -m alembic -c operational/alembic.ini upgrade head
python -m alembic -c operational/alembic.ini current
python -m alembic -c operational/alembic.ini history
```

Alembic применяет транзакционную ревизию `0001_operational` и фиксирует её в `alembic_version`. Повторный upgrade на head оставляет строки на месте. Последующие изменения получают новые ревизии. Для воспроизведения в **пустой синтетической БД** создайте владение и выделенный источник один раз:

```sql
INSERT INTO workspace(id,name) VALUES ('00000000-0000-4000-8000-000000000001','Synthetic');
INSERT INTO client_project(workspace_id,id,name) VALUES
 ('00000000-0000-4000-8000-000000000001','00000000-0000-4000-8000-000000000003','Demo');
INSERT INTO source(workspace_id,project_id,id,source_key,kind,origin_label) VALUES
 ('00000000-0000-4000-8000-000000000001','00000000-0000-4000-8000-000000000003',
  '00000000-0000-4000-8000-000000000002','demo','synthetic_demo','packaged fixture');
```

```bash
w=00000000-0000-4000-8000-000000000001
s=00000000-0000-4000-8000-000000000002
python scripts/build_public_demo_dataset.py --verify
python operational/backfill_demo.py --workspace "$w" --source "$s" --dry-run
```

Dry-run читает нормализованную синтетическую DuckDB в read-only и не подключается к PostgreSQL. В отчёте есть счётчики, ключ объекта, хэши и будущие ID. Для этих UUID ожидаются 1 058 отзывов, 12 точек и manifest SHA `8cacefacc9feb493c7482b491728c6a315680110d7adddafbb2af3a88ea1ce5a`. Для apply заранее разместите **отдельную копию** файла по возвращённому ключу. В примере используется новый приватный каталог. Сохраните его для проверки восстановления.

```bash
objects=$(mktemp -d)
sha=85ca0756ca60f56c735360ab46632d8893287635e7fec1a28548f97dae5fcfe2
mkdir -p "$objects/$w/sha256"
cp demo/reviewscope_demo.duckdb "$objects/$w/sha256/$sha"
chmod 400 "$objects/$w/sha256/$sha"
python operational/backfill_demo.py --workspace "$w" --source "$s" --object-root "$objects" --apply
```

- Процедура принимает только побайтово проверенный упакованный артефакт. Переносит все 1 058 нормализованных записей, поля и метаданные, 12 внутренних точек и mappings, initial versions, квитанцию и запечатанный manifest. Векторы остаются в исходном формате в копии DuckDB. Публичного URL, загрузки или автоматического копирования в blob storage нет. Ключ вычисляется как `<workspace UUID>/sha256/<file SHA-256>`.
- Подтверждённая внешняя идентичность здесь означает ID **синтетического источника**. В нём обязательны review_id и reviewer_id. Операционная модель допускает NULL для неизвестного автора и внешнего ID. Будущий импортёр должен сохранять отдельные неподтверждённые идентичности; для передачи в старый NormalizedReview строку без автора потребуется отдельно учесть по правилам PR-09/10. Подставлять общего автора нельзя.
- Квитанция UUIDv5 учитывает W, S, версию процедуры и SHA файла. Под блокировкой строки source перенос атомарно публикует весь состав. Два параллельных повтора дают один `applied` и один `already_applied`. Повтор сверяет checksum размещённого объекта и исходный manifest. Первый импорт требует пустого синтетического источника. Счётчики описывают сохранённые строки DuckDB. Дата получения исходной выгрузки и заявленное покрытие остаются NULL. Произвольный backfill реальных файлов, карантин, новые версии при последующих поставках и определение полноты относятся к PR-09/10.

## Резервная копия и восстановление

1. Остановите публикацию новых ссылок и переходы хранения до окончания согласованной копии. Сохраните custom-архив PostgreSQL **и** неизменяемые байты по тем же относительным ключам в отдельное защищённое место. Один SQL-архив хранит только ссылки. Для артефактов с pending_deletion перед копированием уточните фактическое наличие байтов. Намеренные удаления требуют отдельного учёта при восстановлении.
2. Для синтетического примера ниже переменная `objects` указывает на исходный каталог. Проверки SHA выполняются внутри отдельного корня. Архив и перечень ключей содержат служебные данные и хранятся вне Git и CI-артефактов.

```bash
umask 077
backup=$(mktemp -d)
pg_dump -Fc -f "$backup/operational.dump" "$PGDATABASE"
psql -XAt -v ON_ERROR_STOP=1 -c "
 SELECT duckdb_sha256 || '  ' || duckdb_key FROM snapshot
 UNION SELECT checksum || '  ' || object_key FROM artifact WHERE storage_state <> 'deleted'
" > "$backup/checksums"
cp -a "$objects" "$backup/objects"
(cd "$backup/objects" && sha256sum --check --quiet "$backup/checksums")
```

3. Восстановите архив в **новую пустую** БД и объекты в отдельный корень. При несовпадении SHA, отсутствии файла или ошибке FK оставьте исходный контур на месте. Перед переключением проверьте размер доступных артефактов по size_bytes, число членов каждого снимка, digest и путь от сохранённого запуска до его исходной версии. Зафиксируйте cutover отдельно.

```bash
createdb -T template0 reviewscope_pr07_restore
pg_restore --single-transaction --exit-on-error --no-owner --no-privileges \
  -d reviewscope_pr07_restore "$backup/operational.dump"
restored=$(mktemp -d)
cp -a "$backup/objects/." "$restored/"
(cd "$restored" && sha256sum --check --quiet "$backup/checksums")
PGDATABASE=reviewscope_pr07_restore python -m alembic -c operational/alembic.ini current
```

Ревизия forward-only. Автоматический downgrade возвращает ошибку до удаления данных. Для отката восстановите согласованную **предмиграционную** копию в отдельную БД с её версией приложения либо выпустите новую исправляющую миграцию. Старый локальный API может продолжать читать исходный файл независимо. Проверка DDL и архива работает на реальном PostgreSQL. [Инструкция PostgreSQL по pg_restore](https://www.postgresql.org/docs/16/app-pgrestore.html)

## Проверки и дальнейшие границы

```bash
bash operational/test-postgres.sh -s
ruff check .
git diff --check
python scripts/build_public_demo_dataset.py --verify
```

Нужны установленные PostgreSQL server/client с `pg_config`, право создать приватный Unix-сокет и обычный непривилегированный пользователь. Скрипт создаёт отдельный кластер во временном каталоге, отключает TCP и по завершении убирает только свой кластер. CI выполняет эту проверку отдельной задачей; обычная задача сохраняет offline HTTP contract до установки ML и полный pytest. PostgreSQL-тесты проверяют все нормализованные поля, реальный pg_dump/pg_restore, два конкурирующих импорта, отказ записи истории и cross-workspace FK. Они проверяют сохранность ссылок на файлы и переносимость байтов, а не полномочия пользователей.

**BLOCKED_REAL_SOURCE** и **BLOCKED_CLIENT_PILOT** сохраняются. PR-08 отвечает за фактические access checks. PR-09/10 — за разрешённый импорт, историю поставок и эволюцию снимков. PR-11/12 — за worker, публикацию результатов и контролируемое удаление. В PR-07 эти операции представлены только схемой.

## Ревизия 0004_delivery_history

Ревизия привязывает каждую review_identity к существующей source_location, добавляет привязку анонимных наблюдений, типизированные event_date/event_at и третий счётчик в import_batch. Таблицы import_row и delivery_authorization закрыты для rs_runtime. Для новых поставок существующий snapshot хранит каноническую проекцию, формат указан в filters. Состав, фактический SHA и восстановление приведены в [контракте](snapshot-contract.md) и [инструкции оператору](snapshot-operations.md).
