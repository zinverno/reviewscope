## Принятый контракт 0021

Кабинет использует TLS API `/api/v1/workspaces/{workspace}/projects/{project}/monitors`. Источник обязателен для каждой операции. Тело записи ограничено 4096 байтами, требуется same-origin CSRF. Схемы запросов и ответов доступны через OpenAPI приложения.

| Операция | Контракт |
|---|---|
| Создать, изменить, архивировать | POST в каталог, `/{id}/versions`, `/{id}/archive`. Изменение и архив требуют `expected_version_id`. Чужая область получает 404, конфликт редакций — 409. |
| Открыть монитор | GET в каталог или `/{id}`. Для исторической версии передаётся `version_id`. Отдельное поле хранит последнюю попытку. Последний успех определяется порядком регистрации допущенной поставки и её UUID, затем временем запуска. |
| Выбрать данные | GET `/{id}/versions`, `snapshots`, `history`. Страница содержит точные total, offset и до 25 строк. Единственная выборка — все принятые позиции поставки одного источника. Неизвестная выборка получает 422. |
| Запустить | POST `/{id}/runs` с version_id, snapshot_id, необязательным parent_run_id и idempotency_key. Получаем оба UUID запуска. Повтор в той же сессии получает 200. Другой смысл ключа, одновременный второй запуск редакции и повтор уже успешного target получают 409. Сохраняются квоты PR-11. |
| Проверить | GET `/{id}/runs/{run}` и `/{id}/runs/{run}/delta`. Опубликованная квитанция имеет собственный SHA-256. Страница содержит предыдущий и целевой UUID версии и происхождение переиспользованной строки. Отмена использует обычную команду PR-11. |

### Импорт и расчёт

Оператор PR-10 и browser_claim берут SHARE по авторизованной workspace до блокировки source. После ожидания проверяются действующие полномочия. Enqueue, CAS версии и архив берут workspace writer в начале транзакции. Предварительная проверка файлов через broker завершается до открытия записывающей транзакции. Для нескольких допусков предшественников используется порядок source_id, checksum. Отдельные workspace имеют собственные строки блокировок.

В журнале поставки relation между identity и version закреплена составным внешним ключом. Сравнение связывает принятые позиции с sealed snapshot_member по snapshot и version UUID. Stable ID относится к точному источнику и месту. Batch-local наблюдения имеют собственную привязку batch/position. Изменение одних метаданных создаёт новый version UUID и требует расчёта. Кардинальности обеих сторон проверяются при публикации.

Для monitor_run фиксируются обе версии, снимок, digest файла/снимка/manifest, predecessor и его artifact/rows SHA. Сервер определяет смысл по сохранённым версиям. Успешный predecessor должен принадлежать той же редакции, а поставка — предшествовать выбранной по порядку регистрации. При иной редакции выполняется полный проход. Изменение фактического runtime также переводит расчёт в полный режим. По 32 UUID за раз worker переносит только совпавшие строки из опубликованного результата, с исходным SHA машинной строки и прежним decision_run_id. Для пропусков используется обычный дочерний scorer PR-22. Пустые тексты входят в accepted и исключаются из eligible. Файл результата, все decision_row и monitor_receipt публикуются общей fenced транзакцией. После потери lease временные строки и их provenance очищаются. Повтор проходит с новым lease.

Машинная квитанция содержит знаменатель eligible, digest delta и provenance, полный rows_sha256 PR-22, runtime и категориальные счётчики. PR-23 сохраняет собственные редакции проверки человека при соответствующем decision_run_id. Монитор использует машинный профиль. Редактирование human revision не меняет квитанцию и не переносит человеческие метки на следующую поставку.

### Допуски и жизненный цикл

Оператор допускает checksum отдельно для evidence, candidate, decision и monitor. Поле `browser_admission.monitor_allowed` по умолчанию false. Права инициирующей сессии и доступ к области перепроверяются перед stage и публикацией. Отзыв допуска предшественника скрывает зависимую историю. Broker проверяет контрольные суммы файлов выбранной поставки и родителя. Каталог и страницы доступны через scoped функции, приватные таблицы закрыты для runtime, upload и worker.

Owner export включает определения, привязки, опубликованные квитанции и provenance в выбранной области. Очистка выполняется штатным retention operator. Старый dump восстанавливается в новый кластер с актуальным независимым deletion ledger, отдельным хранилищем и проверенным access seal. Уничтожение внешних резервных копий требует отдельного подтверждения.
