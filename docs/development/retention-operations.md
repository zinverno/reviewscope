# PR-12. Оператор локального профиля

Поддерживаемый контур — Linux, локальный PostgreSQL, приватное хранилище с fsync, hard link, flock и O_TMPFILE для передачи ZIP. Защищённые каталоги управляются доверенным оператором. На разных машинах или сетевой ФС требуется отдельная проверка согласованности. В этом профиле нет автоматического обслуживания внешних backup.

## Подготовка

1. До изменения существующего контура получить подтверждение владельца, проверить восстановление PostgreSQL с ACL и соответствующий архив объектов на отдельной машине или в изолированном кластере. Зафиксировать системный идентификатор, версии, контрольные суммы, места, полномочия и пределы удаления. Реальные файлы пока закрыты для пилота.
2. Роли `rs_runtime` и `rs_worker` остаются как в PR-08/11. Предварительно создать отдельную LOGIN-роль `rs_retention NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE NOREPLICATION` без членства и владения объектами. На БД действуют запреты TEMP/CREATE, в public закрыт CREATE. Миграции выполняет доверенный владелец схемы. Оператор подтверждения работает через отдельное локальное соединение как rs_retention. Сервисам выдаются только их DB-логины. В раздельных процессах предоставить 8001 read-only mount независимого свидетельства и закрыть ему mount исходных файлов; проверка изоляции процессов конкретного хоста остаётся за оператором. Проверить реальные параметры ОС, конфигурацию сокета, доступ к журналу/файлам и отсутствие сторонних писателей; в синтетическом профиле процессы под одним доверенным Unix UID.
3. Закрыть оба приватных обслуживающих процесса. На новом внедрении 0006 выполнить `python -m alembic -c operational/alembic.ini upgrade head`. Каталог для независимого свидетельства заранее создать с 0700 вне любых резервируемых DB/object roots. Передать абсолютный путь будущего файла в `RS_RETENTION_LEDGER`. Однократно выполнить `python -m operational.retention initialize` под владельцем БД. Сохранить выведенный digest в независимом операционном учёте. Обеспечить продолжительность жизни реестра до истечения самой старой допустимой копии. Резервировать его отдельно и проверять последнюю подтверждённую версию с хранителем.
4. Импорт обслуживает канонические поставки через локальный сокет с прежней явной авторизацией. Для старого backfill, у которого delivery_object_root отсутствует, сначала установить проверенный root соответствующего архива. При невозможности подтвердить владение или найти файлы операция блокируется. Сервис 8001 и worker требуют доступного актуального свидетельства. Для отсутствующего реестра нет автоматического создания. Обновить команды запуска из PR-08/11 переменной `RS_RETENTION_LEDGER`.
5. Настроить сбор логов до допуска данных. У HTTP-сервера отключён access log с URL. Для PostgreSQL проверить `log_statement=none`, `log_min_error_statement=panic`, `log_parameter_max_length=0`, `log_parameter_max_length_on_error=0`, отсутствие логирования запросов по длительности, auto_explain и сторонних трассировщиков с параметрами. Не направлять исключения драйвера, proxy access logs, cookies, команды с приватными путями и дампы процесса в общий сборщик. Реальные установки требуют сверки конфигурации и журналов отдельно.

## Ручная приёмка на синтетике

Использовать сессию owner 8001 и заголовки Origin текущего сервиса и X-RS-CSRF=1 для изменяющих запросов. Все примеры ниже предполагают уже проверенный локальный PGHOST. Файлы передачи должны размещаться за пределами архива в проверенном каталоге получателя с 0700.

1. Получить `GET /api/v1/workspaces/{w}/sources/{s}/retention`. Для отсутствующего правила увидеть unset и null. Установить подтверждённое правило через PUT. Выполнить `POST …/retention/sweep` с UUID idempotency_key. Для неизвестного покрытия ожидается BLOCKED_RETENTION_POLICY.
2. Отправить `POST /api/v1/workspaces/{w}/retention` с полями `action,kind,target,idempotency_key`. Для action=export проверить владельца назначения. Исполнить `python -m operational.retention export --request REQUEST --root PRIVATE_ROOT --owner-handoff OWNER_DIR`. Открыть `OWNER_DIR/REQUEST.zip` и проверить [manifest и содержимое](retention-export.md). Повтор возвращает контрольную сумму той же выдачи. Статус доступен по `GET …/retention/{request_id}` владельцу текущего workspace. Для независимой новой выборки нужен новый ключ.
3. С action=erase выбрать source, project или workspace. Проверить таблицы, SHA, сохраняемые общие ссылки, текущую резервную политику и отдельное подтверждение владельца. Записать краткое основание в закрытый операторский журнал. Выполнить `python -m operational.retention confirm --request REQUEST --preview-sha256 PREVIEW --root PRIVATE_ROOT`. При изменении графа получить новый preview с новым ключом. Проверить отказ старой ссылки и публикации по старому lease. После удаления workspace его membership тоже исчезает; дальнейший статус проверяет оператор.
4. Завершить `python -m operational.retention purge --request REQUEST --root PRIVATE_ROOT`. При grace_pending дождаться 60 секунд от создания сироты и повторить. Файлы с общими ссылками остаются читаемыми из другого источника. Идентичные SHA в другом workspace остаются побайтово теми же. Отдельно проверить, что выданная внешняя копия по-прежнему учитывается как external_uncontrolled.
5. После обрыва между fsync реестра и commit повторить confirm с теми же аргументами. После обрыва на unlink повторить purge. При ошибке ФС/контрольной суммы изолировать каталог, проверить права, тип, хэш и независимую копию. Возобновлять после выяснения причины. SQL-маппинг, отключение триггеров и ручное выставление completed не входят в процедуру.

## Восстановление из независимой копии

1. В момент согласованного backup остановите writers. Хранитель резервной копии фиксирует PostgreSQL dump и полный инвентарь каждого физического object root, включая все workspace, использующие этот root. Формат JSON в UTF-8 показан ниже. Ключ объекта — SHA-256 его байтов, значение — число байтов. Пустая область представляется пустым объектом. Хранитель отдельно сохраняет SHA-256 точных байтов файла inventory, соответствие dump, время и происхождение поколения. Сверка с digest, вновь вычисленным из предложенного оператору каталога, не устанавливает происхождение.
2. До обслуживания остановите 8001, worker, importer и retention-оператора. Восстановите dump в новую БД с ограниченными ролями, ACL и отозванным TEMP у PUBLIC. Подключите независимый **актуальный** реестр запретов и актуальную контрольную сумму прав, полученную хранителем через `access-seal` в рабочем контуре. Для старого формата v1 хранителю потребуется seal из ранее проверенного рабочего контура. При утрате полномочий, реестра или подтверждения его свежести оставьте экземпляр закрытым.
3. Для каждого физического root выполните подготовку в каталоге доверенного оператора. Путь назначения должен отсутствовать, включая пустой каталог. Вход, назначение, inventory и каталог реестра располагаются в приватных областях вне PGDATA. Допускаются локальные ext4, XFS, Btrfs или tmpfs с xattr, однозначным корнем файловой системы и одним монтированием устройства в доверенном Linux mount namespace. Подтома, сетевые ФС и неоднозначные mount alias дают отказ. Для долговременного применения нужен носитель с подтверждённой долговечностью fsync. Tmpfs используется в одноразовых тестах.
4. Передайте SHA квитанции из результата подготовки в `recover`. Для нескольких физических архивов повторите `--receipt`. Если workspace появился и был полностью удалён после dump, укажите его UUID при подготовке соответствующего root через `--erased-workspace`. Неизвестная область блокирует активацию. На одном root действуют пределы 256 workspace, 20 000 объектов, 256 МиБ на файл и 4 ГиБ суммарно. Предел inventory — 4 МиБ.

```json
{"version":1,"backup_id":"00000000-0000-4000-8000-000000000001","workspaces":{"00000000-0000-4000-8000-000000000002":{}}}
```

```sh
python -m operational.retention prepare-restore \
  --source "$ARCHIVED_OBJECTS" --destination "$NEW_ROOT" \
  --inventory "$INVENTORY" --inventory-sha256 "$TRUSTED_INVENTORY_SHA" \
  --latest-sha256 "$TRUSTED_LEDGER_HEAD" --access-sha256 "$CURRENT_ACCESS"
python -m operational.retention recover --receipt "$RECEIPT_SHA" \
  --latest-sha256 "$TRUSTED_LEDGER_HEAD" --access-sha256 "$CURRENT_ACCESS"
```

5. До выдачи квитанции прерванное назначение остаётся изолированным. Повтор подготовки требует другого свободного имени. Храните квитанции, инвентари и реестр в отдельном закрытом каталоге хранителя. Службы должны использовать один доверенный mount namespace и стабильную идентичность каталогов. Выдайте потребителям только чтение свидетельства и необходимые для их роли полномочия. Перенос, потеря xattr, подмена каталога, отсутствие доступа к свидетельству или невозможность проверить ФС закрывают соответствующий путь. Смена каталога после начала replay требует заново восстановить исходный dump в изолированную БД. Сбой до последнего DB commit допускает повтор с тем же набором квитанций и независимо подтверждённым текущим head, включая уже записанный новый head. Не изменяйте checkpoint вручную.
6. После replay проверьте новый digest у хранителя, отказ старым токенам и lease, скрытие удалённых metadata и чтение соседней области с новой сессией. Завершите `purge` восстановленных заявок на соответствующих подготовленных копиях. Сверьте результат с инвентарём и независимым рабочим архивом. Срок удаления архивных поколений учитывается отдельно.

## Истечение поколений backup

Инвентаризировать полные и инкрементные копии, реплики, WAL, object-store versions, снимки дисков, архивы журналов и ключи. Для каждого поколения записать контролирующую сторону, подтверждённую дату последнего хранения и допускаемое окно ротации. Создать новую полную пару PostgreSQL + объекты из очищенного состояния, независимо восстановить её с актуальным реестром, подтвердить SHA и отсутствие клиента. После отдельного согласования вывести старые поколения из ротации, получить доказательства уничтожения/криптостирания или истечения immutable lock во всех местах. До подтверждения последнего подконтрольного поколения состояние **BACKUP_ERASURE_NOT_VERIFIED**, верхняя дата для реального развёртывания неизвестна. Удаление пользовательских скачиваний находится у их получателей.
