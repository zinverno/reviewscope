## Что показала проверка

В PostgreSQL 18.6 созданы два одноразовых кластера и два пустых приватных каталога объектов. Тест создал workspace, выполнил pg_dump и pg_restore, передал независимую копию в штатный recover и проверил результат штатного отказа access_review_required. В deletion ledger было ноль событий. Контрольная точка обслуживания осталась закрыта, независимое свидетельство сохранилось, оба каталога остались пустыми. В восстановленной БД поле workspace.delivery_object_root уже содержало новый каталог. Проверка сохранения исходной привязки завершилась ошибкой.

Причина видна в границах транзакций. Первая транзакция recover читает прежний каталог, записывает предложенный каталог и сохраняет отпечаток предложенного набора. Проверка актуальных прав выполняется позже. При повторе после отказа исходным для сравнения становится значение из уже изменённой строки. Код проверяет новый кандидат сравнением путей с этой строкой. Отпечаток предыдущей попытки также вычислен из предложенных ей каталогов. [Привязка каталогов](https://github.com/zinverno/reviewscope/blob/6b861d59cb33d2f519c0f97702c6793664813012/operational/retention.py#L407-L429), [проверка прав](https://github.com/zinverno/reviewscope/blob/6b861d59cb33d2f519c0f97702c6793664813012/operational/retention.py#L439-L451).

Ошибка оператора при повторном выборе может привести к привязке действующего архива. После активации восстановленный каталог ссылок может отличаться от действующего. При очистке файлы проверяются относительно ссылок в обслуживающей БД. При ошибочной привязке это создаёт риск удаления файлов, которые всё ещё нужны действующему контуру. Это вывод из кода. Новый тест закончился на чтении состояния после отказа. [Сверка ссылок перед физической очисткой](https://github.com/zinverno/reviewscope/blob/6b861d59cb33d2f519c0f97702c6793664813012/operational/retention.py#L279-L307).

## Проверки для ревью

В окружении проекта выполнить из worktree:

```sh
bash operational/test-postgres.sh -k 'owner_lifecycle_restore or restored_access_requires_fresh_session or rejected_activation_preserves_original_root_for_retry' --tb=short
```

Два ранее существующих сценария проверяют активацию разрешённой копии, закрытый доступ при ошибке и старые сессии. Новый сценарий отдельно проверяет привязку, которую следующий вызов использует для защиты исходного хранилища. Он должен стать зелёным при исправлении. Если защита будет реализована независимым реестром идентичностей, проверку следует направить на его инвариант.

Для возобновления кампании нужно доказать, что любая прерванная активация сохраняет проверяемое различие рабочего архива и восстановленной копии. При неизвестном происхождении каталога доступ к публикации и очистке остаётся закрытым. Ручная приёмка на двух независимых синтетических поколениях должна проверить отказ с сохранением исходного архива, повтор на подтверждённой копии и неизменность данных второго поколения.
