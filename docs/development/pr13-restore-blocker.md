# Проверка физической независимости перед PR-13

У базы `6b861d5` смена имени рабочего root и восстановление старой БД могли сделать рабочий архив кандидатом для orphan sweep. Даже актуальные deletion ledger и checksum состава прав сохраняют значения при переносе файлов. Коммит `791433a` закрепил выбранное назначение при повторе. Сохраняется требование заново развернуть dump при неизвестной прерванной привязке.

Первое назначение создаёт команда `prepare-restore`. Она копирует байты по независимо закреплённому inventory, делает fsync и перечитывает содержимое. Защищённая запись у хранителя связывает новый root, nonce, inode и mount ID, подкаталоги workspace, проверенный инвентарь и файлы, целевой экземпляр PostgreSQL, права и свежий deletion ledger. Хранитель закрепляет исходные уникальные ID монтирований при их выделении и назначает отдельный каталог для новых поколений. Проверка одного видимого устройства в текущем namespace сама по себе недостаточна для установления происхождения. При первом replay и повторе проверяются квитанции и полный инвентарь. Существующие каталоги отклоняются. Файловая очистка после активации повторно сверяет root и пространство SHA конкретного workspace под блокировкой публикации.

## Проверка на синтетических объектах

```sh
bash operational/test-postgres.sh -s -k 'owner_lifecycle_restore or restore_root_boundary'
```

В сценарии owner создаются A и B на общем root, два источника с общими SHA, старая копия, новая поставка и новые запреты. После переноса живого root сверяются SHA-256 и пары device/inode каждого объекта. Попытки использовать перемещённый root по имени, повторно создать его и подставить его вместо подготовленного root отклоняются до изменения сессий и состояния replay. Второй postmaster восстанавливает dump, повторяет запреты и очищает исключительно новую копию. Тест выводит числа объектов, SHA и inode для сопоставления в конкретном запуске.

Отдельные сценарии проверяют разрыв копирования и SQL commit, изменение прав, отсутствие и повреждение квитанции, замену каталога и настоящий bind mount в изолированном mount namespace. Решения о доступе к реальным данным, сохранности backup и объединении PR принимает владелец. [Процедура оператора](retention-operations.md)
