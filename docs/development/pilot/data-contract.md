# Два снимка отзывов по одной точке

Единица поставки — **два отдельно полученных снимка** из одного разрешённого источника и паспорт каждого снимка. Подойдут две последовательные месячные выгрузки или две накопительные выгрузки с известными границами. Разделение одного сегодняшнего файла по месяцам даёт две группы публикаций, но не доказывает повторяемость выгрузки.

## Минимальный вход

CSV в UTF-8 с заголовком или JSON в UTF-8 с массивом объектов тех же полей. Идентификаторы — строки, пустые ячейки CSV и `null` в JSON означают отсутствие значения. Если поставщик использует другие названия, записать соответствие полей в паспорте, исходник сохранить без правок в течение разрешённого срока.

| Поле | Как читать |
| --- | --- |
| `source`, `source_place_id` | Обязательны. Постоянный код системы/формы и точки в пределах клиента. Если у одной формы ровно одна точка, допустима документированная привязка на уровне файла. |
| `source_review_id` | ID записи у источника, если он доступен. Ключ сопоставления включает клиента, источник, точку и этот ID. |
| `text`, `rating` | Полный текст с исходной пунктуацией и оценка в исходной шкале. Шкалу и преобразование в 1–5 описать отдельно. Отзыв без оценки допустим. Оценку без текста учесть в охвате выгрузки, исключить из знаменателя анализа текста. Усечение текста пометить. |
| `published_at` | Дата публикации у источника. Для собственной формы разрешено взять дату отправки ответа и указать в паспорте `event_basis=submitted`. Если источник показывает только дату правки, обозначить это отдельно. |
| `observed_at` | Время получения снимка с часовым поясом. Можно задать для всего файла. Локальный импорт имеет отдельное время `imported_at`. Повторный импорт не меняет дату наблюдения. |
| `source_url`, `reviewer_id` | Необязательны. Ссылка только из разрешённого источника, без токенов и временных подписей. При отсутствии ссылки основанием служит запись в закрытом снимке. ID автора принимается лишь при подтверждённом праве и необходимости, имя и контакты не нужны. |

**Паспорт снимка.** Указать `snapshot_id`, время наблюдения, локальную контрольную сумму файла, источник, точку, часовой пояс, смысл даты, интервал `[начало, конец)`, способ и фильтры экспорта. Зафиксировать режим (за период или накопительный), ограничения истории, счётчик источника при тех же фильтрах, число страниц и завершение пагинации, если применимо. Отметить `full / partial / unknown` и основание. Значение `full` относится только к заявленным фильтрам и доступным у источника записям. Для утверждения о полноте нужна сверка со счётчиком либо документированное подтверждение исчерпания доступной выборки с проверкой ограничений.

## Сопоставление и контроль

1. **Сначала посчитать потери.** Для каждого файла записать число исходных строк/объектов, принятых, точных дублей с подтверждённой идентичностью и отклонённых. Эти три группы дают исходное число. Для каждого отказа указать причину. Отдельно посчитать отсутствие ID, текста, даты, оценки и признаки усечения у принятых записей. Некорректный тип, конфликт значений одного ID в одном снимке, ошибочная дата или оценка вне заявленной шкалы требуют явной диагностики и решения. Строка без даты может быть принята для аудита, но исключается из месячного подсчёта. Нечитаемый файл получает ошибку целиком.
2. **Развести строку, отзыв и версию.** Повтор того же файла в том же снимке (тот же паспорт и контрольная сумма) даёт прежний результат. Новый самостоятельно полученный снимок сохраняет собственное наблюдение, даже при совпадении байтов. Один ключ и изменённые текст или оценка в следующем снимке — новая наблюдавшаяся версия прежнего отзыва. Хранить ссылку на снимок и номер строки/индекс объекта. Предыдущий результат можно воспроизвести по использованной версии.
3. **Без ID источника** присвоить строке локальный ключ `(snapshot_id, номер записи)`. При наличии стабильной закрытой ссылки можно согласовать и проверить её как ключ. Совпадающие текст, дата или их хэш дают лишь кандидата для ручной сверки. Не объединять автоматически похожие или одинаковые анонимные строки. Если неопределённость влияет на знаменатель, указать её и отложить сравнение.
4. **Без автора** оставить `reviewer_id` пустым, исключить строку из расчётов по авторам. До PR-09 аналитик сверяет такие записи в закрытой таблице по ключу отзыва/строки. Текущий нормализатор требует ID автора, а DuckDB заменяет записи с одним `review_id`. Поэтому исходные снимки ведутся раздельно, число пропусков ядра показывается отдельно. Общий фиктивный автор исказил бы историю. [Нормализация](../../../src/reviewscope/ingestion/normalize.py) · [Хранилище](../../../src/reviewscope/storage/duckdb_store.py)
5. **Сравнить одинаковые условия.** Отнести отзыв к месяцу по дате события в согласованном часовом поясе точки. Для времени без смещения нужен документированный пояс, для даты без времени сохранить исходную точность. Снимки должны иметь один источник, точку, смысл дат, фильтры, сопоставимую задержку выгрузки и подтверждённое покрытие сравниваемых периодов. Зафиксировать версию определения аспекта и метода решения. Одну жалобу считать один раз на отзыв внутри аспекта. Показывать `число жалоб / число пригодных текстовых отзывов`, пропуски и неясные решения. При несовместимых условиях показать два описательных результата и причину отказа от динамики. Пропажа записи из частичного снимка означает «не наблюдалась». Удаление требует явного основания у источника.

## Синтетический пример для ручной сверки

Все идентификаторы и тексты ниже придуманы для проверки контракта. Два накопительных CSV по одной точке, пояс `Europe/Moscow`, шкала 1–5, дата события — публикация. Условный источник отдаёт все записи с 1 сентября до 1 октября (A, счётчик 3) и до 1 ноября (B, счётчик 6), правые границы исключены. Оба файла получены в 09:00 первого числа следующего месяца с одинаковыми фильтрами. Статус `full` задан **только для этого примера**.

**Снимок A**

```csv
source,source_place_id,source_review_id,text,rating,published_at,observed_at,source_url,reviewer_id
synthetic,p1,r1,На табло уже было готово. У стойки простоял ещё десять минут.,3,2026-09-08T17:10:00+03:00,2026-10-01T09:00:00+03:00,,
synthetic,p1,r2,Долго готовили суп. Принесли сразу после кухни.,3,2026-09-12T12:00:00+03:00,2026-10-01T09:00:00+03:00,,
synthetic,p1,r3,Ждать не пришлось.,5,2026-09-21T13:00:00+03:00,2026-10-01T09:00:00+03:00,,
```

**Снимок B**

```csv
source,source_place_id,source_review_id,text,rating,published_at,observed_at,source_url,reviewer_id
synthetic,p1,r1,Уточню — ждал приготовления. Готовое отдали сразу.,3,2026-09-08T17:10:00+03:00,2026-11-01T09:00:00+03:00,,
synthetic,p1,r2,Долго готовили суп. Принесли сразу после кухни.,3,2026-09-12T12:00:00+03:00,2026-11-01T09:00:00+03:00,,
synthetic,p1,r3,Ждать не пришлось.,5,2026-09-21T13:00:00+03:00,2026-11-01T09:00:00+03:00,,
synthetic,p1,r4,Пакет уже стоял за стойкой. Выдали только после второго напоминания.,4,2026-10-03T18:20:00+03:00,2026-11-01T09:00:00+03:00,,
synthetic,p1,,С заказом всё успели. Задержали уже на выдаче.,3,2026-10-10T14:00:00+03:00,2026-11-01T09:00:00+03:00,,
synthetic,p1,r6,Напиток готовили долго. Готовый стакан забрал сразу.,4,2026-10-17T08:40:00+03:00,2026-11-01T09:00:00+03:00,,
```

**Ожидаемый разбор.** A — 3 принятые строки из 3, B — 6 из 6. Отклонённых и точных дублей внутри файлов нет. У одной строки B нет ID источника, у всех отсутствует автор. В сентябре по версии A жалоба есть в `r1` (1/3). В октябре по версии B — в `r4` и в пятой записи данных B (2/3). Остальные формулировки описывают приготовление либо отрицают ожидание. Сентябрьский `r1` в B отредактирован. Он остаётся сентябрьским и не меняет зафиксированные 1/3 в A. Если бы B содержал только «последние три» без доказательства покрытия октября, разницу публиковать было бы нельзя.
