# PR-20 · Устойчивое определение проблемы клиента

## Решение и ключи

Аспект принадлежит проекту внутри workspace. У двух филиалов или поставок одного проекта может быть одна и та же постановка вопроса. UUID создаёт PostgreSQL при подтверждении. Совпадение названий, формулировок или векторов не объединяет записи.

| Запись | Адрес и назначение |
|---|---|
| `aspect` | `(workspace_id, project_id, aspect_id)`, автор, дата, номер текущей версии и состояние архива. |
| `aspect_version` | Тот же ключ плюс последовательный `version_no`. У каждой редакции свой `version_id`, digest, автор, время, origin и неизменяемый payload. Отложенный FK текущего номера проверяется при фиксации транзакции. |
| Тема PR-15 | Точный адрес публичного freeze из dataset SHA, overview result, source result, place и номера кластера. Номер имеет смысл внутри этого результата. |
| Задача PR-05 | `problem_id` и `definition_version` обозначают экспериментальную задачу в offline benchmark. |
| Запуск PR-19 | `(workspace_id, snapshot_id, run_id)`. Алгоритмическая версия по-прежнему `candidate-search-1`. Опциональная `candidate_params.aspect` фиксирует project/source/aspect/version/digest. |

```text
workspace / project ── aspect ── definition v1, v2, …
              └── source ── snapshot ── candidate run ── artifact SHA
                                          └── exact definition version + digest
```

## Сохранение и происхождение

Клиент вводит короткое имя (1–120 символов), определение (1–2000) и по 1–10 включающих и исключающих примеров (1–500). Суммарный предел — 16 384 байта для UTF-8 сериализации payload в PostgreSQL. Сохраняются исходные символы, пробелы и порядок примеров. Полностью пробельные строки, NUL, невалидный Unicode, неверные типы, лишние и повторяющиеся поля, повтор одного примера внутри или между группами отклоняются. Сравнение строк точное. Нормализация NFC и преобразование регистра не применяются.

Digest версии равен lowercase hex SHA-256 от UTF-8 строки `aspect-definition-1`, затем LF и `payload::jsonb::text` в PostgreSQL. Ключи объекта фиксированы: `name`, `definition`, `include`, `exclude`. Экранирование, пробелы и порядок ключей задаёт вывод JSONB. Смена сериализации потребует нового префикса. Digest удостоверяет содержимое. Принадлежность определяет составной FK; происхождение хранится отдельно.

Сохранение с одним ключом идемпотентности в рамках проекта, тем же автором, действием, исходной версией и содержимым возвращает исходные UUID. Другая команда с этим ключом получает 409. Явное сохранение с новым ключом создаёт редакцию даже при идентичном содержимом; digest тогда совпадает. Запись сериализуется с изменением членства и проверяет `expected_version` под блокировкой. Из двух правок одного основания проходит одна. Архивация с подтверждением необратима через кабинет. Завершение уже принятого запуска и чтение истории разрешены по действующему допуску. Новая редакция и новый запуск архивного аспекта получают 409.

В публичном синтетическом обзоре ссылка темы открывает черновик для выбранного проекта. Видны кластер, фразы, число отзывов и адрес freeze. Автор самостоятельно задаёт границы и подтверждает POST. Отмена или открытие страницы не создаёт записи. Миграция фиксирует допустимые адреса из упакованного обзора; произвольный JSON или источник с другой версией отклоняется. Новая редакция сохраняет собственный provenance, прежняя — исторический. При исчезновении исходной темы карточка показывает недоступность. Перестановка или новый расчёт кластеров не обновляют аспекты. Для канонического снимка предложения тем пока недоступны.

В синтетическом тесте A описывает очередь до приёма заказа, B — задержку передачи уже готового пакета. Долгое приготовление выходит за обе границы. Для B фраза «Готовый заказ выдали сразу» исключает претензию, а неопределённое «Ждали сорок минут» оставляет этап неизвестным. Один отзыв может обсуждать обе проблемы. Полные A/B, включая отрицания, зафиксированы в `operational/tests/test_aspects.py`. Это примеры для автора определения. Независимые qrels, stance, частота жалоб и решения по отзывам потребуют других данных.

## API и поиск

Префикс каталога — `/api/v1/workspaces/{w}/projects/{p}/aspects`. GET возвращает 25 кратких записей от `offset`; POST создаёт аспект. По адресу `/{aspect}/versions` доступны постраничная история и POST новой редакции. GET `/{aspect}/versions/{version}` читает одно определение и его примеры. POST `/{aspect}/archive` требует UUID ожидаемой версии. Создание возвращает 201, точный повтор и архивация — 200. Записи требуют Origin, CSRF и ключ идемпотентности. Действуют общие безопасные коды ошибок кабинета.

Запрос кандидатов по-прежнему принимает `source_id, query, role, mode, k, idempotency_key`. Для выбора версии клиент добавляет только `aspect: {aspect_id, version_id}`. Сервер выводит проект из источника, проверяет допуск снимка, находит версию и вычисленный БД digest. Генерируемые колонки запуска обеспечивают составные FK на источник проекта, снимок источника и версию аспекта. Идемпотентность включает binding. Свободные запросы и исторические артефакты сохраняют исходную форму и байты. Кабинет подписывает их «Аспект не назначен». Переиспользование старой формулировки с новой версией создаёт другой запуск.

Перед запуском кабинет показывает определение и оба списка примеров. Формулировку вводят отдельно. Пределы PR-19 остаются 2048 UTF-8 байт и для MiniLM 128 токенов вместе со служебными. Дочерний ML-процесс получает только исходные четыре параметра поиска. Родитель включает точный binding в документ перед хешированием. PostgreSQL при публикации сверяет его с immutable запросом наряду с проверками SHA, scope, текста и offsets из PR-19. Лимит 65 536 байт, lease, cancellation, retry и проверка допуска при публикации сохраняются. Чтение проверяет checksum объекта через broker, digest запроса и binding по БД. Ответ bound run содержит старую query и неизменяемую редакцию; точный первичный фрагмент открывается с возвратом в тот же run.

PR-21 сможет получить frozen definition вместе с кандидатами конкретного запуска и границами их текста. Для PR-22 понадобятся оценка каждой подходящей версии в корпусе, evidence span, позиция и явное состояние неизвестности. Членство в выдаче PR-19 само по себе этих ответов не даёт.

## Допуск и жизненный цикл

| Доступ | Условия |
|---|---|
| Owner, analyst | Чтение, авторство, редакция и архивация в активном workspace, в проекте этой области без реальных источников. Независимую настройку можно прочитать по её адресу после удаления последнего источника. |
| Viewer, другая область, истёкшая или отозванная сессия | Закрытые определения, примеры и запуск поиска недоступны. |
| Получатель bound run | Дополнительно требуются актуальные evidence/candidate admission конкретных байтов, совпадающие источник и снимок, доступный объект и действующий локальный witness. |
| Worker, broker | У ролей отсутствует сырой доступ к таблицам каталога. Worker видит адрес версии в параметрах своей lease. Broker читает точный артефакт по прежнему краткоживущему билету. |
| Retention operator | Только допущенный owner export и область подтверждённого запроса через RLS. |

Локальный TLS и синтетический профиль обязательны. Транзакции API проверяют независимый witness и перед приватным SQL bind проверяют безопасные log settings. SQL-функции с фиксированным search path перепроверяют session proof, actor, workspace и проект; блокировки сохраняют порядок с отзывом членства. Каталог и история включают RLS, разрешения runtime ограничены функциями. Ошибки и метрики не содержат определения и query. В URL живут идентификаторы. React отображает пользовательский текст как текстовые узлы.

Настройки создаёт человек. Автоматическое копирование приватных цитат и private source-derived proposals не поддерживаются. Автор может вставить чувствительный текст вручную; форма предупреждает об этом. Source erase удаляет runs, артефакты и их binding; независимая настройка остаётся в проекте. Project/workspace erase каскадно удаляет аспекты и все редакции, включая архив. Отдельного hard delete аспекта в кабинете нет. Полное удаление доступно оператору через действующий протокол удаления проекта или workspace.

В `owner-export-2` выгрузка проекта или workspace содержит закрытый каталог и все его версии по явному списку полей. Source export содержит только разрешённые runs с их точными ссылками; содержимое определений исключено. Прежний каталог авторизаций и защиты PR-12 продолжает действовать. Новый access record v3 фиксирует ACL, RLS, SQL функций, ключи, формулы генерируемых полей и триггеры аспекта. После upgrade требуется новый независимый seal для restore. Оператор восстанавливает отдельную копию через актуальные ledger, seal, receipt и изолированное object root; до открытия доступа выполняется replay удалений и проверка каталога. Физическое стирание backup остаётся непроверенным.

## Воспроизведение

В отдельном checkout установить штатные test extras и собрать кабинет по CI. Выполнить `ruff check .`, `python scripts/build_public_demo_dataset.py --verify`, `python -m pytest tests/test_api.py` и полный `python -m pytest -o addopts="" -q`. Для PostgreSQL использовать только `bash operational/test-isolated.sh`. Выборка `-k 'test_aspect or reviewer_context_upgrade or cabinet_native'` покрывает авторство, выдачу, точную миграцию, изолированный TLS и restore; полный прогон включает исходные 10k, generic/custom plans и fencing. С подготовленной offline MiniLM включить `RS_MEASURE_DENSE=1` и воспроизвести `python scripts/benchmark_candidates.py --minilm`. Для отдельного эксперимента PR-05 — `python scripts/benchmark_retrieval.py --minilm`. В `prototypes/reviewscope-ui` выполнить npm ci/lint/typecheck/test/build и обе конфигурации test:browser.
