# PR-11 · Фоновые задания

**NEEDS_WORKER_CONTRACT_REVIEW · BLOCKED_REAL_SOURCE · BLOCKED_CLIENT_PILOT.** Результат первого задания — проверка целостности и числовая сводка конкретной поставки. Для A учитываются три наблюдения, все три без автора. Результат можно получить после выхода аналитика из сессии. Публикацию выполняет отдельный локальный процесс.

Исходный раздел «PR-11 — Фоновая обработка и публикация результата» от 20 ноября 2026 года задаёт четыре обязательства. Состояния и пределы проверяет PostgreSQL-профиль, повтор порций — тесты убийства и отмены worker, атомарность — failpoint до SQL COMMIT и выбор последнего успеха, диагностику — события worker_stage. Один run_id остаётся основанием для будущей однократной записи квоты PR-38.

## Вход и результат

`snapshot_integrity_and_summary_v1` / engine `1` / definition `summary-1` / model `unused`. Параметр отбора фиксирован как `accepted_in_delivery`. Область данных задают workspace и snapshot. У PR-10 `filters.format=canonical-json-v1`, а историческое имя поля с SHA осталось `duckdb_sha256`. Worker проверяет следующее.

1. Права заявителя, соответствие workspace/source/batch, SHA SQL-манифеста и упорядоченное равенство version_ids с snapshot_member.
2. Файл поставки и три паспорта/конфигурации по их SHA, fingerprint PR-09, формат и версии, декларацию покрытия и уравнение квитанции. Ввод ограничен 4 МиБ и 10 000 позициями, каждый файл конфигурации — 32 КиБ.
3. Заголовок и каждую строку канонического объекта до LF сравнивает **побайтово** с детерминированной проекцией соответствующих записей PostgreSQL. Страница из максимум 64 версий сортируется по UUID. Проверяются ожидаемый UUID по позиции, итоговый SHA и конец файла. Повтор уже изменённого отзыва использует версию данного снимка.
4. Сводку кодирует JSON UTF-8 с отсортированными ключами, компактными разделителями и одним LF. В ней есть UUID run/snapshot/source/batch/workspace, manifest, SHA канонического объекта и четырёх входных объектов, fingerprint и параметры. Повтор попытки для того же run даёт те же байты. Новый ключ заявки даёт новый run и новые байты с его UUID.

| Поле | Числитель и знаменатель |
|---|---|
| observations, quarantined, confirmed_duplicates | Принятые наблюдения, карантин и точные повторы внутри поставки соответственно / все входные позиции. |
| delivery_exclusions | Позиции данного кода причины / все позиции. Коды причин могут пересекаться. |
| eligibility.unknown_author, usable_text | Без сохранённого ID автора, с непустым текстом после strip соответственно / все члены снимка. |
| eligibility.known_rating, comparable_date | Приводимая к звёздам оценка, пригодная дата соответственно / все члены снимка. |
| rating_distribution | Для проверенной шкалы [1,5] каждый числитель — число оценок с этой звездой / все пригодные оценки. При неподдерживаемой шкале поле равно null. При пустом знаменателе сохраняется числовая пара 0/0. |
| metric_exclusions | Пропуски и непригодные значения каждого вида / все члены снимка. Одна запись может попасть в несколько строк. |

Пригодность даты следует PR-09. Календарный день или абсолютный момент допускается при basis published/submitted. Неопределённый локальный момент, неизвестная или недопустимая дата исключаются. Поля event_basis, coverage, coverage_mode, covered_from/until сопровождают счётчики. Full относится к декларации оператора в рамках зафиксированных фильтров, partial, unknown и null сохраняются отдельно. Фильтры и основание оператора можно перепроверить по SHA паспорта. Пригодный текст означает возможность дальнейшей обработки. Авторские признаки имеют статус AUTHOR_METRICS_UNSUPPORTED. Для ML действует ANALYSIS_NOT_AVAILABLE. Сравнение периодов, качество поиска, авторство и намерения здесь не оцениваются.

## Идентичность заявки и API 8001

Клиент задаёт случайный UUID idempotency_key до отправки и сохраняет до получения ответа. UNIQUE(workspace_id,request_key) и транзакционная блокировка workspace сериализуют приём. Сравниваются snapshot_id, job_kind и engine_version. Остальные параметры однозначно заданы этой версией. Один ключ принадлежит рабочей области, участники которой совместно работают с результатами. Совпадение внешних ID или ключа в другой области не связывает заявки. Новый запуск требует нового ключа. Для PR-38 единицей списания может служить UNIQUE(workspace_id,run_id) в будущей транзакции учёта. Повторный POST возвращает исходный ID даже после исчерпания лимита. Учёт платежей отсутствует.

Все пути ниже имеют префикс `/api/v1/workspaces/{workspace}`. На TLS cookie __Host-rs_session устанавливает локальный login. Изменяющие запросы требуют точный Origin и X-RS-CSRF. Ответы получают X-Request-ID и Cache-Control: no-store. Для GET/POST действуют текущая серверная сессия и membership. Архивная область закрыта для запуска и отмены.

| Метод и путь | Роль и результат |
|---|---|
| POST /runs | Owner/analyst. JSON содержит snapshot_id, idempotency_key, job_kind, engine_version. 202 новая заявка, 200 повтор, 409 конфликт, 422 неподдерживаемая новая спецификация, 429 лимит. |
| GET /runs/{run_id}/status | Owner/analyst/viewer. Подробный статус фоновой заявки и метаданные разрешённого артефакта. |
| POST /runs/{run_id}/cancel | Owner/analyst, пустое тело. 200 при отмене или при принятии запроса отмены running. Отмена уже cancelled идемпотентна, после другого terminal возвращается 409. |
| GET /snapshots/{snapshot_id}/latest-summary | Последний succeeded для указанного снимка, по finished_at и UUID. 404 до первой успешной публикации. |
| GET /runs и GET /runs/{id} | Прежняя схема PR-08 из трёх полей, включая исторические записи. |

Неизвестная и чужая область/объект дают одинаковый 404. Viewer получает 403 при записи в своей области. Новые обработчики используют пул rs_runtime с transaction-local контекстом и RLS. Функции записи повторно проверяют текущего участника под блокировкой. Runtime читает только разрешённые поля статуса, UUID, SHA и размер доступного опубликованного результата. Тела и ключи объектов доступны доверенному оператору. Логи HTTP содержат шаблон маршрута. [Контракт PR-08](access-contract.md)

## Попытки и публикация

- Допускаются четыре активные заявки и 20 новых за скользящий час в workspace. На БД доступны два одновременных действующих lease. Это инженерный профиль для одного локального узла. DB сериализует только короткое выделение двух слотов. FOR UPDATE SKIP LOCKED защищает выбор строки.
- queued → running увеличивает attempt и выдаёт свежий случайный lease_token. Heartbeat продлевает lease на 15 секунд по часам БД. Worker проверяет владение и запрос отмены между блоками ввода до 64 КиБ и страницами версий. Ограничение производной проекции — 64 МиБ. Статус содержит stage, processed, total. При неизвестном знаменателе total равен null. Stage и счётчик служат контрольной точкой наблюдения. Следующая попытка проверяет неизменяемый вход сначала.
- Временная недоступность файлов, SIGTERM или истёкший lease возвращают работу в queued с задержкой 1 и 2 секунды после первой и второй попыток. После третьей попытки исход failed. При потере соединения открытая SQL-транзакция откатывается, другой процесс подбирает просроченную работу. Один poll восстанавливает до одной истёкшей попытки. Для постоянного восстановления нужен работающий polling-процесс.
- Отмена queued немедленно ставит cancelled. Для running БД фиксирует cancel_requested. Следующая контрольная точка, публикация или recovery переводят работу в cancelled. После прекращения доступа заявителя работа завершается с ACCESS_REVOKED. Выход из браузерной сессии сам по себе не отзывает членство.
- Проверенный PR-10 object root принимает результат через fsync и hard link под SHA без замены. После перечитывания байтов worker вызывает worker_step. Одна транзакция блокирует права и run, сверяет текущий lease, флаг отмены, готовность прогресса и manifest, вставляет artifact и переводит run в succeeded. Устаревший nonce получает stale. Прерывание после hard link допускает единственный новый объект этого содержимого без SQL-ссылки. Согласованность гарантируется при доверенных DBA, worker, владельце файлов и исправной файловой системе. SHA в статусе удостоверяет публикацию на момент commit. Текущую сохранность байтов проверяет восстановительная процедура.
- Конечные коды — CANCELLED, ACCESS_REVOKED, LEASE_EXPIRED, STORAGE_UNAVAILABLE, WORKER_STOPPED, INTEGRITY_ERROR, UNSUPPORTED_FORMAT, RESOURCE_LIMIT, UNSUPPORTED_VERSION, INTERNAL_ERROR. Успех имеет reason=null. Лог этапа содержит только этап, номер попытки, строки, длительность, состояние и показания памяти. Время и RSS конкретного теста относятся к его хосту.

## Граница будущего AnalysisEngine

Отдельный job_kind и версия должны сначала доказать формат immutable DuckDB, соответствие SHA и полному membership, шкалу оценок, временную основу, происхождение ID авторов и покрытие пригодных строк. Новая проекция должна иметь собственную версию и связь с исходными version ID. После проверки совместимый объект можно передать DuckDBStore(read_only=True) и AnalysisEngine с проверенным precomputed-only кэшем по образцу API 8000. Для строк без автора нужен отдельный проверяемый контракт знаменателя и авторских сравнений. Текущий worker не импортирует движок, DuckDB или модель. [Контракт снимка](snapshot-contract.md)

Ревью владельца охватывает границу доверия worker, знаменатели и трактовку времени, лимиты, восстановление и повторное использование run_id. Правила хранения, удаления и обращения с orphan — отдельный PR-12. [Операторская процедура](worker-operations.md)
