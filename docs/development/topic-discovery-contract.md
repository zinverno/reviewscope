# Кандидаты тем на загруженном снимке

## Протокол до оценки

База PR-24 `735d62d97a130c935ec5b912eba1220f4d36f0ee`, дерево `8bcd3402b3abfc260aa4f39d460a5861a39a9997`. Корпус в `tests/fixtures/topic-discovery.tsv` содержит авторские синтетические сцены. Dev описывает кассу и печь, test использует другие семейства формулировок, history — отдельный более ранний период. Малый holdout позволяет сверить каждую пару. Золотая единица — уникальный нормализованный текст с одной проблемой. Mixed и unknown исключаются из метрик с указанием числа. У шума, похвалы и отрицания нет положительных пар. Эти строки учитываются в ложных объединениях. Дубликаты, длинный хвост и нагрузка проверяются отдельно.

Профиль `supported-phrase-v1` работает в PostgreSQL на CPU, без весов, случайности и попарной матрицы. Нормализация ICU lower, свёртка пробелов. Слова — непрерывные буквы/цифры. Признак — слово длины 4–64 либо два соседних таких слова. Короткое слово разрывает биграмму. Для каждого уникального текста выбрать один признак с поддержкой от трёх разных нормализованных текстов. Сначала биграммы, затем более редкий признак, затем порядок C. После распределения группа с менее чем тремя различными текстами уходит в шум. Каждая версия входит максимум в одну тему. Бюджет синхронной публикации — 512 версий, 8192 байта на версию и 256 КиБ текста. Выход за бюджет до вычисления даёт RESOURCE_LIMIT без частичной публикации. Критерии co-membership precision ≥0,80 и recall ≥0,60 одновременно. Пропуск пары в шуме считается пропуском. Zero denominator даёт null. Редкая тема с поддержкой меньше трёх отмечается отдельно. Параметры на holdout не меняются. Semantic вариант не входит в кабинетный профиль.

## Область, владение и жизненный цикл

Сервер разрешает операции на допущенных synthetic bytes PR-25 при действующих evidence и candidate. В режиме всех текстов классификатор не участвует. Во втором режиме исследуется одно точное определение через immutable PR-22 run, опционально с frozen PR-23 revision. Выбираются неясные или not_mentioned машинные исходы и спорные/неясные ручные исходы.

Результат принадлежит snapshot, редакция кандидата — результату, источник членства — точная версия snapshot_member. Повторы запроса учитываются отдельно. Состав редакции неизменяем. Одно действие потребляет открытые редакции и атомарно записывает причину, родительство и новые редакции. Подтверждение привязывает точную версию аспекта PR-20. Для нового определения применяется тот же валидатор. Проверка аналогии связывает редакцию с историческим снимком того же источника. При чтении действуют оба допуска. Удаление следует обоим родителям. Авторское определение остаётся настройкой проекта до удаления проекта. Сгенерированные слова и цитаты в определение автоматически не копируются.

## Состав и идентичность

Единица ввода — принятая версия отзыва. Сначала сверяются journal, отсортированные UUID в snapshot и snapshot_member, manifest и независимый объект. По каждому UUID брокер хеширует UTF-8 строку `version_id:content_sha256:text_sha256\n` в порядке канонического объекта. Для NULL вместо SHA текста используется дефис. SQL независимо получает тот же SHA. У каждого отзыва сохраняются исходный SHA, длина в Unicode code points, SHA нормализованного текста, причина отбора и назначение. Диапазон свидетельства полуоткрытый, от 0 до длины исходника. CRLF, регистр и emoji в оригинале сохраняются. Представители — максимум пять разных нормализованных текстов, минимальный UUID из каждой группы, затем по UUID. Повторы увеличивают число версий, поддержка считает разные тексты. Плотной матрицы и разбиения на перекрывающиеся окна здесь нет.

`N_input = N_accepted + N_quarantine + N_confirmed_duplicate`. Из принятых отдельно показаны blank, eligible и исключённые из выбора. Для полного результата `N_selected = N_clustered + N_noise` и `N_not_processed = 0`. В режиме одного определения решение берётся по всем UUID только из указанного завершённого запуска. Ручное событие из выбранной опубликованной редакции имеет приоритет. Dispute, unclear, mixed и topic_uncertain попадают в исследование, остальные проверенные версии получают явную причину исключения. Для машинного результата также включается not_mentioned. Источник каждого исхода виден в selection_counts и строках результата. Поддерживаются пустой результат, недостаточная поддержка и весь корпус в шуме. Превышение бюджета останавливает публикацию до вычисления.

Технический ключ запроса, UUID результата, UUID редакции кандидата, content key и UUID версии аспекта имеют разное назначение. Content key — SHA-256 UTF-8 PostgreSQL `jsonb::text` массива `["candidate-1", binding, sorted_member_uuids]`. Binding включает workspace/project/source/snapshot, SHA объекта и manifest, ordered source rows SHA, паспорт метода (SHA определений SQL, версия PostgreSQL и ICU, единица, минимум и отбор), при наличии — PR-22 run, artifact/rows SHA, точное определение и PR-23 revision/digest. Числовая метка, порядок входного списка и новый ключ запроса в content key не входят. Повтор в той же области сохраняет прежний результат и его ручную историю. Смена версии текста, снимка или профиля задаёт другую область сравнения.

## Работа в кабинете и HTTP

Из обзора снимка открывается исследование всех пригодных текстов. Из результата PR-22 или опубликованной редакции PR-23 можно открыть выборку по определению. У кандидата доступны представители, весь состав по страницам, точный оригинал, исходная и производные редакции, действия и проверка истории.

Общий префикс — `/api/v1/workspaces/{w}/snapshots/{s}/topic-discovery`. Каждый метод принимает source UUID. У записи обязательны UUID ключа идемпотентности, Origin и CSRF. Приватный кабинет работает через TLS, выдача помечается no-store.

| Метод | Действие |
|---|---|
| GET по префиксу | Возможность публикации, причины ограничения, сохранённые результаты выбранного режима. Возможны decision_run и human_revision. |
| POST по префиксу | Собрать и опубликовать один целый результат или вернуть отказ. |
| GET /{result} | Manifest и список редакций. С candidate_id — состав, SHA, представители, события, родители и дети. offset задаёт начало страницы, version открывает точный оригинал. historical_snapshot выбирает конкретные исторические квитанции. digest закрепляет результат. |
| POST /{result}/actions | Явные confirm, merge, split, reject с expected_open, причиной и параметрами действия. |
| POST /{result}/history-checks | Поиск для candidate_id и historical_snapshot. Решение по найденной версии передаёт expected_check, version и accept. |

Страница вмещает до 25 элементов, история — до пяти записей, общий ответ — до 64 КиБ. Текст открывается отдельно по ссылке на доступную страницу/представителя/исторический hit. При уходе с вкладки кабинет очищает частные данные, проверяет область при возврате и периодически во время просмотра. Причины, цитаты и термы передаются вне URL. Предел на workspace — 128 новых команд за час. Новый ключ даёт 201, точный повтор того же актора — 200. Повтор с другим содержимым или устаревший expected_open даёт 409, некорректное разбиение — 422, превышение размера входа — 413. Недоступный оригинал или расхождение байтов закрывает доказательную выдачу.

Объединяются 2–8 открытых редакций одного результата, состав равен объединению UUID. Разделение принимает 2–8 непустых непересекающихся частей и максимум 96 версий суммарно. Кабинет позволяет разложить полностью показанный состав до 25 версий на две части. Поддержка каждой ручной части считается заново, одна версия допустима. Событие закрывает родителей для новых действий и сохраняет исходный состав для просмотра. Confirm требует точную активную версию существующего аспекта либо вручную заполненные название, границы и примеры. Сохранение определения и связи — одна транзакция. Новые произвольные определения могут получить UNSUPPORTED_DEFINITION в классификаторе PR-22. Reject сохраняет причину и автора. Каждый переход указывает редакции, актора и время БД.

## Историческая проверка

Аналитик явно выбирает один другой допущенный снимок того же источника. Для обоих периодов сохраняются UUID, SHA, фактические известные даты, покрытие и границы поставки, digest фильтров и основания времени. Используются дата публикации или UTC-дата известного момента публикации. Если дат нет, результат HISTORY_NOT_AVAILABLE. Пересечение периодов, изменение фильтров, основания или метода дают HISTORY_NOT_COMPARABLE. Неполное покрытие, неизвестные даты части версий, quarantine, дубли или записи вне заявленного периода дают HISTORY_PARTIAL. HISTORY_CHECKED относится только к выбранному сопоставимому периоду.

Алгоритм representative-overlap-1 ищет слова и биграммы представителей среди пригодных исторических версий с известной более ранней датой. Сохраняются число просмотренных, до пяти совпадений по числу разных общих признаков с UUID как разрешением равенства, оригинальные интервалы и SHA. Отсутствие совпадения — ограниченный результат этого поиска. Аналитик может сохранить OBSERVED_IN_SELECTED_HISTORY или ANALOGY_REJECTED для конкретного найденного UUID. В квитанции остаётся ссылка на исходную проверку. Для новой оценки можно провести отдельный поиск. Численная оценка бизнес-динамики по этим данным отсутствует.

## Допуски, публикация и восстановление

Миграция 0019 добавляет opt-in topic_discovery_allowed DEFAULT false на SHA конкретной поставки. Для чтения/записи требуются active workspace, synthetic source, owner/analyst, актуальные session и retention witness, evidence и candidate grants. При выборе PR-22/23 добавляются соответствующие допуски. Брокер с ограниченным билетом сверяет независимый объект, файл, mapping и паспорта. Для истории требуются разрешения на обе стороны при каждом чтении. Блокировки существующих строк прав и сессии сериализуют отзыв с публикацией, ожидаемые редакции и транзакционная блокировка сериализуют конкурирующие команды. SQL сверяет proposed и written SHA и упорядоченный набор UUID до commit. Обрыв до commit откатывает публикацию. У синхронного пути нет очереди и поколения lease.

RLS, фиксированный search_path и ACL разделяют runtime, upload, worker и retention. План удаления учитывает шесть таблиц. После source/project/workspace erase производные составы, термы и события удаляются в той же области. Проверки истории зависят от обоих snapshot. Полный owner export выполняет оператор в исходном контуре, технические ключи повторов исключены. После restore старой копии применяются независимый deletion ledger и текущая печать, выполняется проверка каталога и объектов. Результаты физического удаления резервных копий неизвестны. ## Подтверждение с созданием аспекта · схема 0020

На исходной ревизии [7da72ed](https://github.com/zinverno/reviewscope/commit/7da72ed01b27cbd69418ee9c212583b83767f75f) воспроизведена инверсия порядка блокировок (`REPRODUCED`). На изолированном PostgreSQL 18.6 два авторизованных пользователя работали с реальным импортом и локальным брокером. Наблюдатель читал виды блокировок и связи ожидания. После регистрации каждого ожидания держатель завершал транзакцию. SQLSTATE `40P01` в этих наблюдениях не возник.

| Путь на 0019 | Что уже удерживала транзакция | Чего ждала | Время до наблюдения |
|---|---|---|---:|
| HTTP confirm с новым определением | Workspace SHARE и topic advisory | Workspace UPDATE за другим читателем | 38 мс |
| Прямой scoped SQL confirm | Workspace SHARE и topic advisory | Тот же UPDATE | 34 мс |
| Другая команда topic | Workspace SHARE | Topic advisory той же области | 35 мс |

| Порядок на 0020 | Что проверяется или блокируется |
|---|---|
| Вход в операцию | В HTTP действует shared gate независимого deletion ledger. Проверяются session proof, workspace, доступ к source, допуск точных байтов и существование immutable result. Первичные проверки SQL выполняют обычное чтение. |
| Writer authority | До первого scoped read подтверждение с новым определением вызывает PR-20 `job_writer`. Он берёт UPDATE одной строки workspace и SHARE членства. Обычные create/edit/archive аспекта начинают с того же writer. Чужой workspace может публиковать одновременно. |
| Авторизация и байты | `topic_scope` проверяет snapshot, source, проект, principal, сессию, admission и при наличии PR-22/23 parents. `aspect_scope` проверяет проект. HTTP затем сверяет manifest, SHA и строки через object broker. На GET действует прежний режим чтения. |
| Команда и публикация | Scoped `topic_review` самостоятельно обеспечивает тот же входной порядок. Затем workspace topic advisory сериализует receipt и проверку открытых родителей. Вложенный `save_aspect` уже владеет workspace UPDATE. В одной транзакции фиксируются aspect, v1, событие со ссылкой и digest, receipt, внешние ключи и финальная проверка полномочий. |
| Отзыв и восстановление | Изменения admission/session сериализуются с authority SHARE. Retention использует независимый gate и штатную обработку своей области. После обновления оператор фиксирует текущий access seal. Старая каталоговая печать отклоняется. |

В собственной SQL-транзакции, которая объединяет чтение с таким подтверждением, сначала вызывают `topic_confirm_writer` с точной областью. Это же делает HTTP перед `page_data`. Helper доступен только `rs_runtime`, отказ освобождает полученные им блокировки. Исходная реализация действия доступна только владельцу функций. Миграция обновляет функции и ACL, данные сохраняются.

Регрессии останавливают первый запрос непосредственно перед commit и подтверждают фактическое ожидание второго по `pg_blocking_pids`. Проверяются оба порядка конкурирующих действий, точный replay, разные кандидаты, обычный PR-20 CAS, независимые workspace, отзыв и истечение сессии. Отдельные случаи проверяют потерю объекта или witness, недопустимое определение, разрыв соединения и побайтно эквивалентное содержимое сохранённых записей при upgrade. Время относится к синтетическому стенду.
