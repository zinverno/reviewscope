## Запуск

Из корня репозитория в подготовленном окружении Python ≥3.12:

```sh
python scripts/benchmark_retrieval.py --validate-only
python scripts/benchmark_retrieval.py
python scripts/benchmark_retrieval.py --minilm
```

По умолчанию запускается только символьный TF-IDF. Флаг добавляет MiniLM. CLI включает offline-режим Hugging Face до импорта backend и проверяет файл весов для точной revision в локальном кэше. Отсутствие весов даёт `NOT_RUN_MISSING_WEIGHTS`, отсутствие backend — `NOT_RUN_MISSING_BACKEND`. Ошибка загрузки повреждённой модели или несоответствие контракта прерывает запуск. E5 в этот PR не включён. Локального snapshot multilingual-e5-small при аудите не было (`MODEL_NOT_RUN_OFFLINE`).

Каждый запуск печатает путь к новому `validation_data/benchmarks/run-*/report.json`. Каталог игнорируется Git. Отчёт содержит локальные ID, ранги, оценки и ошибки. Приватный отчёт целиком остаётся у владельца. Хэши трёх файлов реализации, входной fingerprint, параметры, версии, seed и покрытия позволяют сопоставить два запуска. При повторе сравнивайте `methods.*.queries`, `summary_by_mode` и идентичности. Длительности, RSS и имя каталога зависят от запуска.

## Формат и критерии аннотации

Шаблон — публичный JSON выше. Закрытый файл хранится вне checkout либо в `validation_data/private/`. В `manifest` укажите `kind=private`, ID набора, происхождение, ссылку на подтверждённое разрешение для локального анализа, `annotation_source=independent_human`, дату, версию разметки, протокол разделения и заранее согласованный список методов. Для первого вычисления хэша впишите в `fingerprint` 64 нуля.

```sh
python scripts/benchmark_retrieval.py --dataset validation_data/private/retrieval.json --fingerprint
# Владелец вносит напечатанный digest в manifest и сохраняет копию в протоколе оценки.
python scripts/benchmark_retrieval.py --dataset validation_data/private/retrieval.json --validate-only
python scripts/benchmark_retrieval.py --dataset validation_data/private/retrieval.json --split test --minilm
```

Fingerprint — SHA-256 модельного JSON со всеми текстами, qrels, параметрами манифеста и назначениями split, кроме самого fingerprint. Сериализация использует UTF-8, компактные разделители, ключи объектов сортируются, порядок массивов сохраняется, отсутствующие необязательные поля принимают значения по умолчанию. Пересчёт хэша сам по себе не подтверждает права, независимость аннотации или дату фиксации.

- `queries`: уникальный `query_id`, исходный `query_text`, стабильные `problem_id`, `definition_version`, текст определения и `mode`. Для `text_to_text` нужен заранее отложенный пример отзыва с `exemplar_family` вне корпуса поиска. Составьте формулировки до просмотра выдачи.
- `documents`: уникальный `review_id`, полный исходный текст с контекстом, источник, семейство и split. Язык, точка и дата периода допускают null. В v1 индексируется целый отзыв. Отдельная разметка нескольких независимых фрагментов внутри него остаётся за пределами формата. Для `evidence_span` можно сохранить точную подстроку.
- `judgments`: одна запись на пару `(query_id, review_id)`. Аннотатор читает определение и весь отзыв вслепую к выдаче. Оценивает конкретную проблему в этом отзыве. Сначала фиксируются оценки, затем открываются результаты методов.

| Relevance | Stance | Критерий для «готовый заказ долго не выдают» |
|---|---|---|
| 2 | `complaint`, `mixed` | Текст утверждает, что заказ уже был готов и выдачу задержали. Саркастическую похвалу проверьте по описанным событиям. У `mixed` есть эта претензия и другая позиция, например похвала еде или положительная оговорка. |
| 1 | `denial`, `unclear`, `not_applicable` | Отрицание задержки при выдаче, недостаток контекста о готовности либо близкая тема без целевой претензии (например, долго готовили суп). |
| 0 | `not_applicable` | Целевой аспект и близкая к нему тема отсутствуют. Претензия к двойному списанию может получить 2 для другого запроса. |
| null | null | Пара ещё не оценена. Пропущенная пара имеет тот же статус. Размеченное «неясно» получает 1, если текст касается аспекта. |

## Split и независимый тест

Зафиксируйте определения, семейства редакций и почти одинаковых текстов до разбиения. Весь кластер помещается в один split. Для одиночного текста допустим собственный family ID. Валидатор обнаруживает пересечение объявленных семейств и совпадения после casefold и свёртки пробелов. Поиск перефразированных копий и проверка правильности семейств остаются частью подготовки корпуса.

Настройки и отбор кандидатов выполняются на train/dev. До вскрытия независимого test зафиксируйте в закрытом протоколе fingerprint, SHA кода, стек, контракты моделей, шаблоны запросов и K. Для private-набора требуется выделенный test. На holdout CLI требует весь заявленный список методов. Однажды использованный для настройки test требует нового независимого среза для подтверждения.

`future` требует известных дат строго позже всех train/dev/test. `novel_place` требует известных точек, отсутствующих в train/dev/test. Для первой проверки допускаются знакомые точки, для второй — знакомый период. Каждая выполняется отдельным запуском. Смещение отбора отзывов, неполные источники, ошибочные семейства, переиспользованные формулировки запросов и отсутствие независимого арбитража ограничивают перенос результата.

## Методы и расчёт

TF-IDF использует `char_wb`, n-граммы 3–5, float32. Словарь и IDF строятся по документам выбранного поискового корпуса. Запросы и оценки релевантности не участвуют в построении. MiniLM использует [EncodingContract PR-04](embedding-contract.md), commit модели `e8f8c211226b894fcb81acc59f3b34ba3efd5f42`, 128 токенов, 384 компоненты, текст без префикса. Ключ пакета в памяти состоит из ключей PR-04 с разными идентичностями документа, запроса проблемы и внешнего примера. Записей в production DuckDB нет.

Для каждого запроса выполняется точный поиск по всем векторам split после L2-нормализации. Косинус сортируется по убыванию, равенство разрешается по SHA-256 от `[42, review_id]`, затем по ID. Порог не применяется. K берётся из 5, 10, 20, 50 в пределах корпуса. Для корпуса меньше 5 выводится фактический размер.

- **Recall@K** — число документов с оценкой 2 в первых K, делённое на полное число таких документов для запроса. **RR@K** — обратный ранг первого документа с оценкой 2 в первых K, либо 0. **MRR@K** — среднее RR по допустимым запросам. [Recall в trec_eval](https://github.com/usnistgov/trec_eval/blob/master/m_recall.c) · [Reciprocal rank в trec_eval](https://github.com/usnistgov/trec_eval/blob/master/m_recip_rank.c)
- **nDCG@K** — DCG выдачи, делённый на DCG идеальной сортировки всех известных оценок по убыванию при том же K. Слагаемое для позиции (i), считая с 1, равно `(2**grade - 1) / log2(i + 1)`. Оценка 1 даёт частичный выигрыш. [Экспоненциальный gain в XGBoost](https://xgboost.readthedocs.io/en/stable/parameter.html#parameters-for-learning-to-rank-rank-ndcg-rank-map-rank-pairwise)
- Общая группа для этих трёх метрик — **только полностью размеченные запросы с хотя бы одной точной претензией**. Для остальных `metrics=null`. В JSON есть число полностью оценённых, имеющих известный позитив, неполных и вошедших в среднее запросов отдельно для каждого режима. `incomplete_judgments` сохраняется даже при наличии известных позитивов. FP/FN для точного класса и K содержат только установленные ошибки. Для unknown в top-K есть отдельный счётчик.

## Результат синтетического smoke

Fingerprint `6f9aa5c71903156806f9fc594f15aa311cf20b6355f28f1c2d8249479fd32b3f`. В режиме «запрос → отзыв» у всех трёх запросов есть известный позитив, два полностью размечены. Для запроса о сдаче неизвестны 11 из 13 пар. В режиме поиска по примеру полностью оценён один запрос. K=20 и 50 здесь неприменимы.

| Режим | Метод | K | Recall | MRR | nDCG |
|---|---|---:|---:|---:|---:|
| Запрос, 2 допустимых | TF-IDF | 5 / 10 | 0,500 / 1,000 | 0,500 / 0,583 | 0,603 / 0,790 |
| Запрос, 2 допустимых | MiniLM | 5 / 10 | 0,667 / 1,000 | 0,375 / 0,375 | 0,652 / 0,775 |
| Пример, 1 допустимый | TF-IDF | 5 / 10 | 0,667 / 0,667 | 1,000 / 1,000 | 0,802 / 0,817 |
| Пример, 1 допустимый | MiniLM | 5 / 10 | 1,000 / 1,000 | 1,000 / 1,000 | 1,000 / 1,000 |

Для `q-pickup` в top-5 TF-IDF вошли два отрицания, неясный отзыв и отзыв о приготовлении. Пропущены все три точные претензии. MiniLM вернул одну из трёх и пропустил смешанный отзыв `s02` и иронию `s11`. Среди его пяти кандидатов тоже оказались два отрицания. На двух полностью оценённых формулировках эти различия не устанавливают превосходства модели. Все тексты русские, сравнение языков не проводилось.

Один локальный запуск на Ryzen 5 5500U, с двумя доступными CPU, Python 3.14.7, sklearn 1.9.1. Загрузка MiniLM заняла 15,69 с, первое кодирование 13 документов — 1,42 с, повторное чтение пакета из памяти — 0,014 с, построение индекса — 0,006 с. На три запроса потребовалось 0,037 с поиска с сортировкой. У TF-IDF построение словаря заняло 0,009 с, кодирование документов — 0,0014 с. Пиковый RSS всего процесса — 1 198 080 КиБ. JSON дополнительно разделяет первый расчёт запросов, повторный расчёт с загруженной моделью и чтение из кэша. Эти измерения зависят от нагрузки машины.

**Следующий реальный эксперимент.** Владелец подтверждает права на конкретный корпус локально, фиксирует независимый split и организует слепую разметку всех пар тестовых запросов либо документирует неполное покрытие. Для отчёта о реальном тесте аналитик сверяет известные FP/FN с исходным контекстом, приводит размер каждого среза, спорные случаи и границы применимости. Такой эксперимент здесь не выполнялся.
