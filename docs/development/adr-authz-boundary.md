# ADR PR-08 · Граница доступа к рабочему пространству

Статус **NEEDS_AUTHZ_REVIEW**. Операционный сервис слушает loopback на порту 8001. У него собственный OpenAPI и пул PostgreSQL. Старый процесс на 8000 работает с выбранным оператором read-only DuckDB. Для открытого демо оператор использует только упакованную синтетику. Процесс PR-08 не открывает DuckDB и не импортирует аналитическое ядро.

## Кто устанавливает личность

Оператор проверяет человека до создания аккаунта. Одна нормализованная ASCII-учётная запись соответствует одному UUID. Обе ревизии нужны для обновления существующей базы. На `0002_principals` оператор может связать подтверждённую учётную запись с прежним UUID. На `0003_workspace_access` миграция блокирует изменения членств на время проверки и устанавливает FK. Неразрешённое членство останавливает upgrade. Активность аккаунта и активность его членства имеют отдельные состояния.

| Таблица | Содержание и доступ |
| --- | --- |
| principal | UUID, уникальный логин, время создания и состояние. Оператор регистрирует аккаунты. |
| password_credential | Одна случайная 16-байтовая соль и один 32-байтовый верификатор на аккаунт. Таблица закрыта для SELECT приложения. |
| access_session | Первичный ключ — digest сессии. Ссылка на аккаунт, создание, истечение, отзыв. Проверка активного аккаунта при каждом чтении. Деактивация отзывает все его сессии. |
| workspace_membership | Существующий составной ключ, проверенный FK, роль и состояние именно в этом workspace. |
| membership_event | Исходное состояние при миграции и транзакционные события с прежними/новыми ролью и состоянием, UUID субъекта и временем. actor_id — владелец, выполнивший изменение через API. NULL у миграции и действий оператора без пользовательской сессии. Приложению журнал закрыт. |

Сервер вычисляет Argon2id v19 с 64 MiB, тремя проходами, четырьмя потоками и длиной результата 32 байта. Секрет сервера разделён по назначениям префиксами HMAC. Для пароля он получает HMAC-SHA-256 от `password\0` и результата Argon2id. БД сравнивает SHA-256 этого доказательства с сохранённым верификатором. Поэтому чтение строки credential из резервной копии не даёт аргумент для открытия сессии. Для неизвестного аккаунта сервер выполняет тот же KDF со случайной солью. [Параметры Argon2id, RFC 9106](https://www.rfc-editor.org/rfc/rfc9106#section-4)

Браузер получает токен из 32 случайных байтов. Доказательство сессии — hex от HMAC-SHA-256 сервера по `session\0` и ASCII-токену. БД хранит только SHA-256 от ASCII-представления доказательства. Утечка действующего токена из браузера или доказательства из памяти процесса позволяет использовать сессию до её отзыва или истечения. Оба значения секретны. Для списков сессий и аккаунтов у runtime нет прав.

## Две проверки при чтении и изменении

1. Сервер проверяет сессию, ищет активное членство по паре (workspace, principal) и проверяет действие по конечной таблице ролей. SQL получает параметризованный UUID рабочей области. Список workspace всегда фильтруется по подтверждённому principal и ролям чтения.
2. Каждая транзакция под `rs_runtime` проверяет роль, ревизию, наличие таблиц и действие RLS. Пул имеет два соединения. `set_config(...,true)` устанавливает контекст до COMMIT или ROLLBACK. SQL-функция `access_actor` проверяет digest, срок, отзыв и активность аккаунта. Политика membership видит только активные собственные строки и не обращается к membership рекурсивно. Политики метаданных требуют и выбранный workspace, и видимое членство. Знание UUID, включая UUID принципала, не даёт доказательство сессии.
3. У `rs_runtime` есть только SELECT разрешённых столбцов workspace, membership, source, snapshot, analysis_run, версии Alembic и EXECUTE пяти функций ниже. Остальные таблицы операционного содержимого имеют RLS без разрешающей политики и без GRANT. Сервер не передаёт SQL посетителя. DDL, TEMP, членство в других ролях, владение объектами и BYPASSRLS не входят в профиль. Роль миграции владеет схемой и выполняет штатные триггеры и backfill PR-07. [RLS PostgreSQL](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)

| SECURITY DEFINER | Объём полномочий |
| --- | --- |
| login_salt | Получить соль одного активного логина для вычисления KDF. |
| open_session | Записать digest новой сессии только при совпадении доказательства аккаунта. |
| access_actor | Вернуть UUID активного владельца действующей сессии текущей транзакции. |
| close_session | Отозвать только сессию текущего доказательства. |
| change_member | Проверить контекст, роль owner, заблокировать workspace, повторно проверить роль и обновить существующее членство в этой области. Самоизменение через API закрыто. |

У каждой функции фиксирован `search_path = pg_catalog, public, pg_temp`, у PUBLIC отозван EXECUTE, права CREATE в public отозваны у PUBLIC. В вызываемых функциях нет динамического SQL. Триггеры журнала и деактивации используют права вызывающего оператора или проверенной функции изменения. [Защита SECURITY DEFINER](https://www.postgresql.org/docs/18/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY)

## Доверенные стороны и ограничения

Браузер, URL, тело, Origin и заголовки с заявленной ролью не устанавливают личность. Проверка Origin защищает браузерные изменения вместе с заголовком CSRF, cookie и запретом CORS. Приложение доверяет собственному процессу, ключу, библиотекам и локальному узлу. Контроль над процессом даёт доступ к поступающим паролям и токенам. Прямой SQL-доступ runtime опирается на непубличные доказательства. SQL и диагностические каталоги PostgreSQL не предоставляются через HTTP.

DBA, владелец схемы, оператор регистрации, администратор ОС и хранитель резервных копий входят в доверенную область. DBA может менять политики и читать таблицы. Проверка ревизии и RLS выявляет ошибки развёртывания, криптографической аттестации DDL нет. Списки и ответы 404 исключают выдачу чужих идентификаторов через API. Формальной гарантии одинакового времени выполнения запросов или защиты от всех побочных каналов нет. Лимит входа общий для одного процесса. Пилот, публичная эксплуатация и независимый аудит безопасности остаются за пределами этой проверки.
